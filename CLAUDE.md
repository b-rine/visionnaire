# Visionnaire

ML-powered photo app: image captioning + semantic search via a single CoCa ViT-L-14 model on Triton, Qdrant for vector search, FastAPI backend, and React frontend. Photos stored on local disk by default (`STORAGE_BACKEND=local`); Cloudflare R2 available via `STORAGE_BACKEND=r2`.

## Architecture

| Layer          | Service                         | Port                 |
| -------------- | ------------------------------- | -------------------- |
| Inference      | Triton (CoCa ViT-L-14)          | 8000–8002            |
| Vector store   | Qdrant                          | 6333                 |
| Object storage | Local disk or Cloudflare R2     | (local) or (ext.)    |
| Backend        | FastAPI                         | 8080 (→ 8000 inside) |
| Frontend       | React + Vite (served via nginx) | 3000                 |

Everything runs via Docker Compose. GPU (NVIDIA) is required for Triton.

## Running

### Production (full Docker)

```bash
docker compose up --build
```

- Frontend: <http://localhost:3000>
- Backend API docs: <http://localhost:8080/docs>
- Qdrant dashboard: <http://localhost:6333/dashboard>

### Development (hot reload — no rebuild needed)

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up triton qdrant backend
cd frontend && npm run dev
```

Frontend at <http://localhost:5173>. API calls proxy to `localhost:8080` (see `vite.config.ts`). Backend reloads on Python file changes.

## Environment variables

Copy `.env.example` to `.env`. Docker Compose reads it automatically. See [`docs/self-hosting.md`](docs/self-hosting.md) for the production deployment runbook (Oracle Cloud + Cloudflare Tunnel).

## Key design decisions

- **Single model for caption + search**: CoCa ViT-L-14 (`mscoco_finetuned_laion2B-s13B-b90k`) replaces BLIP+CLIP. One Triton model handles captioning, image embedding, and text embedding in the same vector space — so searching with a generated caption gives consistent similarity scores. Originally used the base `laion2b_s13b_b90k` checkpoint, but that's trained only on raw LAION-2B web alt-text and produced tabloid-style hallucinated captions (e.g. inventing celebrity names/relationships) since that corpus is full of clickbait-style alt-text templates. Switched to the MS-COCO-finetuned checkpoint, which is what open_clip's own docs use for captioning — same architecture, fine-tuned on clean literal captions, still trains the contrastive objective alongside captioning so embedding/retrieval quality should hold.
- **Captioning also indexes**: Caption tab calls `/api/photos/upload`, which generates the caption (via `caption_image()`) and the embedding (via `encode_image()`) server-side and returns both. There's no standalone `/api/caption` endpoint — captioning and embedding are separate Triton forward passes (`mode="caption"` runs the decoder and zeroes the embedding output; `mode="encode_image"` does the reverse), so there's no way to get both from one inference call regardless of which endpoint orchestrates it; bundling them into the upload endpoint just means one HTTP round trip instead of two, and the caption is persisted instead of only displayed. Search tab is search-only.
- **Captions persisted in Qdrant payload**: stored on upload, returned by `/api/photos/search` and `GET /api/photos`. On a deduplicated re-upload (same image hash already in the storage backend), the existing caption is read back from the stored payload (`get_photo()`) rather than regenerated.
- **Content-addressed photo IDs**: SHA-256 hash of image bytes → deterministic UUID. Same image uploaded twice returns the same ID without re-uploading (dedup via `storage.photo_exists()`). The dedup branch in `upload_photo_endpoint()` also checks `get_photo_record()` (Qdrant) before short-circuiting — if storage has the object but Qdrant has no matching point (confirmed live: happens when the same R2 bucket is reused across environments, e.g. local dev and prod sharing one `R2_ACCOUNT_ID`/`R2_BUCKET_NAME`, each with its own independent Qdrant collection), it falls through and re-indexes into Qdrant instead of silently returning a blank cached caption and never appearing in the gallery. Storage re-upload is still skipped in that case since the bytes are already there — only `encode_image`/`caption_image`/`upsert_photo` re-run.
- **Pluggable storage backend**: `STORAGE_BACKEND=local` (default) stores photos on disk at `LOCAL_PHOTOS_DIR`; `STORAGE_BACKEND=r2` uses Cloudflare R2. The abstraction lives in `backend/app/services/storage.py` — four async functions (`upload_photo`, `photo_exists`, `delete_photo`, `photo_response`) dispatch to the appropriate backend. `photo_response` returns a `FileResponse` for local (served directly by the backend) or a `RedirectResponse` to a 5-minute presigned URL for R2. `FileResponse` serves files without an extension so the content type is `application/octet-stream`, which browsers handle fine for `<img>` tags. Local default makes the repo runnable without any cloud account signup; R2 backend is kept for production (offloads bandwidth, no backend memory pressure for large files).
- **1 GB storage cap**: Upload endpoint sums `file_size` across all Qdrant points before accepting a new upload. Rejects with 400 if the new file would exceed 1 GiB.
- **Search score threshold & display rescale**: Raw cross-modal cosine similarity from CoCa is inherently compressed by the contrastive training's logit-scale temperature — unrelated pairs typically score ~0.05–0.15 raw, genuinely strong matches ~0.20–0.35. Results below `MIN_SCORE = 0.20` raw cosine are filtered out so unrelated queries return nothing. The remaining raw scores are then linearly rescaled from a fixed `[MIN_SCORE, SCORE_CEILING]` (0.20–0.35) range to 0–100% for display, so a confident match shows as a high percentage instead of a confusing ~30%. This is a **fixed** range, not relative to each query's own top result — commit `bd23094` tried top-result-relative normalization (best match always 100%) and `e30002b` reverted it because unrelated searches also showed 100%. `SCORE_CEILING` is a heuristic for the mscoco-finetuned checkpoint; revisit if real usage data suggests a different calibration.
- **Delete**: `DELETE /api/photos/{id}` removes from the storage backend first, then Qdrant. Frontend has a hover-to-reveal `Del` button with inline Confirm? step.
- **Gallery pagination**: `GET /api/photos` uses Qdrant's `scroll` cursor (not offset/limit math) — `next_offset` is an opaque point-ID string passed back verbatim on the next request. No sort order is applied (Qdrant scroll order, not upload time), acceptable for the current low-volume use case.
- **Manual caption editing via `caption_override`**: `PATCH /api/photos/{id}` (body: `{"caption": str}`) sets a `caption_override` payload field, stored separately from the auto-generated `caption` rather than overwriting it. Search embeddings come from `encode_image()` on the raw photo bytes, not the caption text, so editing a caption has zero effect on search ranking either way — but keeping the original CoCa output around preserves clean image→caption pairs for eventual fine-tuning. `_effective_caption()` (`caption_override or caption`) is applied everywhere a caption is returned (upload, search, list). An empty-string `caption` in the PATCH body clears the override and reverts display to the auto-generated caption. Frontend: edit affordance lives in `PhotoLightbox` (pencil icon → textarea + Save/Cancel); both `Gallery.tsx` and `Search.tsx` wire an `onCaptionUpdated` callback so the edit persists in their local list state across lightbox close/reopen without a full refetch.
- **Static landing page + routing change**: `src/pages/Home.tsx` is a new static page (no API calls) that's now the default route (`/`) — replaces dropping new visitors straight into Caption. Three feature cards (Caption/Search/Gallery) each carry a 1-2 sentence description and a CTA link to that section. `Caption` moved from `/` to `/caption`; `Search`/`Gallery` paths unchanged. Nav is now `Home | Caption | Search | Gallery`.
- **App-wide `✕` = close, `Del` = delete convention**: `PhotoLightbox`'s `✕` used to mean delete, which collided with the natural meaning of `✕` as "close this overlay" once `ApiKeyPrompt` also needed a close affordance — confusing, since the same glyph meant two different (one destructive) things in sibling modals. Fixed app-wide: `✕` now always means close/dismiss; delete is always the text label `Del`. `ApiKeyPrompt` gained a close button (`title="Close"`) plus backdrop-click and Escape-key dismissal (previously required a page refresh). `PhotoLightbox` gained a genuine close button (top-right, `title="Close"`) separate from its delete button, which was relabeled from `✕` to `Del` and moved to bottom-right; `title="Delete photo"` was kept stable so it required no test changes. The Gallery/Search grid-tile hover delete buttons were relabeled the same way for consistency (position/hover-reveal behavior unchanged — a bare thumbnail has no "close" concept, so only the label needed to change there).
- **Modal stacking fix**: confirmed live (final review of the above change) that `ApiKeyPrompt` and `PhotoLightbox` share the same `.lightbox-backdrop` z-index (100), and `App.tsx` rendered `<ApiKeyPrompt>` _before_ `<main>` — so if a delete/edit attempt 401s while a photo is already open in the lightbox, the prompt mounted underneath the lightbox's opaque backdrop, invisible and unusable, and the new Escape-to-close handler on the (invisible) prompt fired first, silently dismissing it instead of letting the user type a key. Fixed by rendering `<ApiKeyPrompt>` after `<main>` instead — same z-index, but later in DOM order so it reliably paints on top of any open lightbox. Also added `padding-bottom: 44px` to `.lightbox-content` (`index.css`) to reserve space for the repositioned `Del` button, which could otherwise overlap the caption row's pencil-icon edit button when a caption was long relative to a small image.
- **Keyword search mode**: `POST /api/photos/search` takes an optional `mode: "semantic" | "keyword"` (default `"semantic"`). Keyword mode does a Qdrant `MatchText` payload filter (`scroll`, not vector `search`) across both `caption` and `caption_override`, OR'd together — a binary text match, not a cosine similarity, so results omit the `score` key entirely (not `null`) and the frontend only renders the score badge `if (score !== undefined)`. Result order is Qdrant scroll order, not relevance-ranked — acceptable since this is a recall backstop, not the primary ranked search. Requires a Qdrant payload text index on both fields, created in `init_collection()` via `create_payload_index` (idempotent, safe to call on every startup). **Tokenizer must be `WORD`, not `WHITESPACE`**: `WHITESPACE` treats `"Alex's"` as one unsplit token, so a query for `"Alex"` would never match it; `WORD` splits on non-alphanumeric characters, producing a separate `"alex"` token that the query can match. Confirmed by a live repro against Qdrant before settling on `WORD`. Frontend: explicit mode toggle on the Search page ("Search by similarity" / "Search by keyword"), not auto-merged with semantic results.
- **Gated Qdrant integration test**: `backend/tests/test_integration_qdrant.py` runs against a real Qdrant instance (Triton/storage stay mocked — Triton needs a GPU + ~1.5GB model download, infeasible on GitHub-hosted CI runners). Marked `@pytest.mark.integration` (registered in `pytest.ini`) and excluded from the default `pytest -v -m "not integration"` run. Each test monkeypatches `vector_store.COLLECTION` to a random throwaway name and deletes it afterward, so it never touches the real `photos` collection. CI runs it as a separate `backend-integration` job using the `qdrant/qdrant` service container (no GPU needed, so this can run on hosted runners unlike a hypothetical Triton integration test).
- **All three containers run as non-root**: backend (`appuser`), frontend (nginx's own built-in `nginx` user), triton (the image's built-in `triton-server` user, uid 1000) — each Dockerfile now also has a `HEALTHCHECK`. Frontend's nginx had to move off port 80 (privileged, root-only) to `8080` — `frontend/nginx.conf` and the `3000:8080` mapping in `docker-compose.yml` both changed accordingly; the host-facing port (3000) is unchanged. Triton's `HOME` moves from `/root` to `/home/triton-server` under the new user, so the `hf_cache` volume mount in `docker-compose.yml` moved from `/root/.cache/huggingface` to `/home/triton-server/.cache/huggingface` to match — verified live that the existing cached model (root-owned from prior root-user runs) is still readable by the new user (world-readable perms), so this didn't force a re-download. If the cache is ever invalidated and Triton needs to _write_ a fresh model into that root-owned tree, it may hit a permission error — not hit yet, but worth knowing if a future model swap behaves oddly.
- **Removed a stray root-level `package.json`/`package-lock.json`**: an accidental `npm install` once run from the repo root (instead of `frontend/`) left a second, unused dependency tree committed to git, carrying an outdated vulnerable `form-data` transitive dependency. Nothing referenced it (`frontend/` has its own, already-current lockfile) — deleted rather than upgraded.
- **`python-multipart` bumped to `0.0.31`**: patches all four CVEs `osv-scanner` flagged on `0.0.27`. **`fastapi` bumped to `0.138.1`** (pulls Starlette 1.3.1) to fix the `python_multipart` import deprecation warning from the old Starlette 0.37.2. **`httpx`→`httpx2==2.5.0`** in dev deps — Starlette 1.3.1's `TestClient` requires `httpx2`. `qdrant-client` still pulls in `httpx` as a transitive dep, so both coexist and Starlette's TestClient emits a deprecation warning pointing to `httpx2` — cosmetic, tests pass. Pattern to know: `osv-scanner` v2 exits with code 127 (`ExitCodeVulnMatcherError`) when its **transitive-dependency resolution RPC** returns an internal error — confirmed in the CI log as `rpc error: code = Internal desc = internal error` during `(extracting as transitivedependency/requirements)`. The extractor choice is **filename-based**, not content-based: any file named `requirements.txt` always goes through the `transitivedependency/requirements` extractor and always calls the resolution RPC, regardless of content. Fixed with two changes together: (1) **pip-compile** puts all transitive deps in `requirements.txt` already pinned, so no resolution is needed; (2) a `lint.definitions` command override in `.trunk/trunk.yaml` switches the trunk plugin to the v2 `scan source` subcommand and passes **`--no-resolve`**, disabling the RPC. The `--no-resolve` flag only exists on `scan source`, not the legacy `--lockfile` format the plugin uses by default. Coverage is preserved because pip-compile already lists every package explicitly.
- **pip-compile lockfiles**: `backend/requirements.in` and `backend/requirements-dev.in` are the source of truth for direct deps. `pip-compile` generates `requirements.txt` and `requirements-dev.txt` with all transitive deps fully pinned and annotated (`# via` comments). To update a dep: edit the `.in` file, then run `pip-compile requirements.in` and/or `pip-compile requirements-dev.in --output-file requirements-dev.txt`. Never edit `requirements.txt` or `requirements-dev.txt` directly — they're generated. `pip-tools` must be installed first: `.venv/bin/pip install pip-tools`.
- **Qdrant healthcheck via bash `/dev/tcp`**: the official `qdrant/qdrant` image has neither `curl` nor `wget`, only `bash`. The compose healthcheck opens a raw TCP connection and sends a literal HTTP GET to `/readyz` via bash's `/dev/tcp` pseudo-device, then greps the response for `200 OK`. Must be invoked as `["CMD", "bash", "-c", "..."]`, not `CMD-SHELL` — Docker's `CMD-SHELL` form always runs via `/bin/sh` regardless of what other shells are in the image, and `/dev/tcp` is a bash-only feature (confirmed live: `CMD-SHELL` failed with `cannot create /dev/tcp/...: Directory nonexistent` under `/bin/sh`). `backend` now depends on `qdrant` with `condition: service_healthy` (was `service_started`), and `frontend` depends on `backend` the same way.
- **Structured logging**: `backend/app/logging_utils.py` — stdlib `logging` (no new dependency) with a custom `JsonFormatter` (one JSON line per record: timestamp/level/logger/message plus any `extra` fields) and a `log_call(operation, context_keys=())` async decorator applied to every Triton/Qdrant/storage service function. The decorator only logs the explicitly named `context_keys` (e.g. `photo_id`, `mode`, `query`) pulled via `inspect.signature(...).bind()` — nothing is logged by default, so large payloads like image bytes or the 768-float embedding are never accidentally written to logs. Logs `"<operation> completed"` with `duration_ms` on success, `"<operation> failed"` with `duration_ms` and a full exception traceback on failure, then re-raises (logging adds visibility, never changes error-handling behavior). Configured once via `configure_logging()` at the top of `main.py`, reading `LOG_LEVEL` (default `INFO`) and writing to stdout. Scope is deliberately limited to the named service-call functions, not a general HTTP request/response middleware. Verified live by killing Qdrant mid-request: the resulting log line carries the operation name, duration, and full root-cause traceback instead of a bare unattributed stack trace.
- **API key auth on write endpoints only**: `backend/app/auth.py` — a single shared static key (`API_KEY` env var), checked via the `require_api_key` FastAPI dependency on `POST /api/photos/upload`, `PATCH /api/photos/{id}`, and `DELETE /api/photos/{id}`. Reads (gallery list, search, single-photo redirect, storage stats) stay open by design — matches personal/local-use scope, not a multi-tenant API. Frontend (`src/apiKey.ts`): no upfront login gate; an axios response interceptor watches for any 401 and surfaces a single global `ApiKeyPrompt` modal (mounted once in `App.tsx`), regardless of which page/action triggered it. The interceptor is installed once from `main.tsx`, not as a module-level side effect, so existing page-level tests (which render page components directly and never execute `main.tsx`) needed zero changes.
- **Rate limiting via `slowapi`**: `10/minute` on upload (Triton-expensive), `30/minute` on delete and caption-edit, `20/minute` on search (no auth, but still rate-limited — see Deploy prep below) — heuristics, same spirit as the `SCORE_CEILING` note above, revisit if real usage disagrees. Keyed by the `X-API-Key` header, falling back to client IP for unauthenticated requests (so brute-force key-guessing also gets capped, not just legitimate-but-overzealous use). slowapi was dormant for 2+ years between releases (`0.1.9` Feb 2024 → `0.1.10`, current) and has an open issue about breaking on newer Starlette — confirmed working on Starlette 1.3.1 (FastAPI 0.138.1); re-check if either is bumped again. The in-memory limiter's counters are reset between tests via `limiter._storage.reset()` (a private attribute — slowapi has no public API for this, tracked as their own open issue #273) since the test suite's `app` instance, and the `Limiter` singleton inside it, persist across the whole pytest session via Python's module cache.
- **GitHub Actions versions**: `actions/checkout@v7`, `actions/setup-python@v6`, `actions/setup-node@v6` — bumped from v4/v5/v4 to suppress Node 20 deprecation warnings on GitHub-hosted runners. `trunk-io/trunk-action` was later pinned to a resolved commit SHA (like every other action in `ci.yml`) as a supply-chain security measure, so it's no longer a floating `v1` tag; the `actions/cache@v4` call inside it still emits one Node 20 warning from trunk's own internals — not fixable from this repo, will resolve when trunk publishes a new v1.x that references cache@v6.
- **Deploy prep for Oracle Cloud + Cloudflare Tunnel**: decided on Oracle's Always Free Ampere A1 tier (1 of 2 free OCPUs/12GB RAM, comfortably under the 1,500 OCPU-hour/9,000 GB-hour monthly cap even running 24/7) for backend + frontend + Qdrant; account converts to Pay-As-You-Go specifically to dodge Oracle's idle-instance reclamation policy (PAYG doesn't change the free allotment, it only allows — and bills for — exceeding it). Triton stays on the local GTX 1060 rather than a rented GPU instance, reached over a private Cloudflare Tunnel; the public-facing app reaches the Oracle instance over a second Cloudflare Tunnel, so TLS is handled at Cloudflare's edge on both legs with no certs to manage anywhere in this stack. `docker-compose.prod.yml` is a standalone file (not a merge override of `docker-compose.yml`) since the topology genuinely differs — no `triton` service, no GPU block, and Qdrant has no host port mapping (closes a real gap: the base compose file publishes Qdrant's port with zero auth of its own, letting anyone who reaches it bypass the backend's API key and rate limiting entirely). `backend/app/services/triton_client.py` gained `TRITON_SSL` (the tunnel hostname is HTTPS) and `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` (sent as headers on every Triton call — confirmed `tritonclient`'s `infer()` forwards arbitrary custom headers, only `Transfer-Encoding` is blocked) to protect the private tunnel with a Cloudflare Access service token, since otherwise anyone who found that hostname could reach Triton directly. `ALLOWED_ORIGINS` env var replaces the hardcoded CORS `allow_origins=["*"]` (defaults to `*` so local dev needs no `.env` change). The manual account/console/DNS steps can't be done from this repo — see [`docs/self-hosting.md`](docs/self-hosting.md) for that runbook.
- **CI/CD pipeline via GHCR**: `.github/workflows/ci.yml` has two jobs appended after the CI suite, both gated to `push` on `main` only. `build-push` (`needs: [lint, backend, backend-integration, frontend]`) cross-compiles ARM64 images via QEMU + Buildx and pushes to `ghcr.io/b-rine/visionnaire-{backend,frontend}` tagged `:latest` and `:<sha>`. `deploy` (`needs: build-push`) uses `appleboy/scp-action` to copy `docker-compose.prod.yml` to Oracle then `appleboy/ssh-action` to pull and restart. Single-file approach over a separate `deploy.yml` triggered by `workflow_run` is intentional — `needs: [...]` in one file is explicit: all four CI jobs must pass; `workflow_run` has subtler semantics where skipped jobs still count as success. `GITHUB_TOKEN` handles GHCR push automatically; `GHCR_PAT` (classic PAT, `read:packages` only) is a separate repo secret for Oracle to pull without storing credentials permanently (script ends with `docker logout`). Oracle machine only needs Docker + `~/visionnaire/.env` + `docker-compose.prod.yml` — no repo clone.
- **ARM64 cross-build**: Oracle Ampere A1 is aarch64; GitHub-hosted runners are x86-64. QEMU + Buildx (`docker/setup-qemu-action@v3` + `docker/setup-buildx-action@v3`) handles cross-compilation. All base images (`python:3.11-slim`, `node:22-slim`, `nginx:1.27-alpine`) have ARM64 variants. GHA layer cache (`cache-from/to: type=gha`) cuts subsequent build times significantly. Required for both `backend` and `frontend` images.
- **Frontend build stage moved off Alpine (`node:22-alpine` → `node:22-slim`)**: confirmed live — the ARM64 cross-build hung indefinitely under QEMU during `npm ci`, with `qemu: uncaught target signal 4 (Illegal instruction) - core dumped` in the logs. This is a known issue with musl-libc native binaries (Vite pulls in Rollup/esbuild, both of which ship prebuilt native binaries) crashing under QEMU's user-mode ARM64 emulation — glibc builds (Debian-slim) don't hit it. Verified locally with `docker buildx build --platform linux/arm64` before pushing: alpine hung/crashed, slim completed cleanly. Only the builder stage changed — the final image still runs on `nginx:1.27-alpine`, which has no npm build step and isn't affected.
- **Token-based cloudflared (no credentials files)**: Both `docker-compose.yml` (home Triton bridge) and `docker-compose.prod.yml` (Oracle public ingress) run `cloudflare/cloudflared` as a Docker service using `tunnel --no-autoupdate run --token ${...}`. The token comes from Zero Trust dashboard → Networks → Tunnels → Create → Docker tab. All routing config (hostname → service URL) lives in the dashboard's Public Hostnames tab — no local config file needed. `--no-autoupdate` prevents the binary from self-upgrading inside the pinned container. The old `cloudflared/` credential-file templates have been deleted. `CLOUDFLARE_TUNNEL_TOKEN` (Oracle public tunnel) and `TRITON_TUNNEL_TOKEN` (home Triton bridge) are the env vars.
- **`docker-compose.prod.yml` uses pre-built GHCR images**: `build:` contexts replaced with `image: ghcr.io/b-rine/visionnaire-*:latest`. Host port mappings removed (`3000:8080`, `8080:8000`) — all ingress goes through the cloudflared tunnel on the same Docker network, so no host mapping is needed. `restart: unless-stopped` on all four services so Oracle survives reboots/crashes without intervention. One-time Oracle setup: `curl -fsSL https://get.docker.com | sudo sh && sudo usermod -aG docker ubuntu`.
- **`triton_client._client()` passes an explicit `ssl_context_factory` when `TRITON_SSL=true`**: confirmed live (first real deploy) that Triton calls over the Cloudflare tunnel failed with `ssl.SSLError: [SSL: SSLV3_ALERT_HANDSHAKE_FAILURE]`, even though `curl` against the same tunnel hostname worked fine. Root cause: `tritonclient.http` sits on `geventhttpclient`, whose `SSLConnectionPool._connect_socket()` only sends SNI (`server_hostname`) and builds a modern `SSLContext` when **both** `ssl_options` and a non-`None` `ssl_context_factory` are passed to the client constructor — otherwise it silently falls back to a legacy `gevent.ssl.wrap_socket()` call with a hardcoded cipher list and no SNI at all, which Cloudflare's edge (SNI-routed) rejects outright. Fix: when `TRITON_SSL` is set, pass `ssl_options={}` and `ssl_context_factory=ssl.create_default_context` — `tritonclient`'s own `HTTPClient.__init__` then auto-populates `server_hostname` into `ssl_options` from the request's `Host` header. Verified end-to-end (TLS handshake + Access token + Triton readiness) via a container built from the same image as production, since the local dev venv's Python 3.12 has an unrelated, cosmetic `gevent.ssl.match_hostname` import failure (removed from Python 3.12's stdlib, still present in 3.11) that made `SSLConnectionPool` fail to even import locally — masking, not causing, the real bug, which only reproduces in the actual TLS path Python 3.11 (prod) takes.

## Backend (`backend/`)

- `app/main.py` — FastAPI app, lifespan initializes Qdrant collection (recreates if vector size changed); wires up the `slowapi` limiter and rate-limit exception handler
- `app/auth.py` — `API_KEY` env var, `require_api_key` dependency (write endpoints), `slowapi` `Limiter` keyed by `X-API-Key` (falls back to client IP)
- `app/routers/photos.py` — POST `/api/photos/upload` (also captions, requires API key + rate-limited), POST `/api/photos/search` (`mode: semantic|keyword`, no auth), GET `/api/photos` (paginated list), GET `/api/storage` (usage stats), GET `/api/photos/{id}`, PATCH `/api/photos/{id}` (caption edit, requires API key + rate-limited), DELETE `/api/photos/{id}` (requires API key + rate-limited)
- `app/services/storage.py` — pluggable storage dispatch: `upload_photo`, `photo_exists`, `delete_photo`, `photo_response`; reads `STORAGE_BACKEND` env var and delegates to local or R2 impl; local `photo_response` returns `FileResponse`, R2 returns `RedirectResponse` to a presigned URL; R2 imports are lazy so R2 env vars are never required when `STORAGE_BACKEND=local`
- `app/services/r2_client.py` — boto3 wrapper for R2 (upload, exists, presign, delete); accessed only through `storage.py`, not imported directly by the router
- `app/services/triton_client.py` — calls CoCa model with mode: `caption` | `encode_image` | `encode_text`; `TRITON_SSL`/`CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` support reaching Triton over a Cloudflare Tunnel once deployed
- `app/services/vector_store.py` — Qdrant ops; VECTOR_SIZE=768 (CoCa embed dim); `get_photo()` retrieves a single point's payload (used for dedup caption lookup); `update_caption_override()` is a payload-only `set_payload` (no vector resend); `search_photos_keyword()` does a `MatchText` `scroll` filter against `caption`/`caption_override`

## Frontend (`frontend/`)

- `src/pages/Home.tsx` — static landing page (no API calls), the default route (`/`); intro + three feature cards (Caption/Search/Gallery) each with a CTA link
- `src/pages/Caption.tsx` — drag/click to upload; single `/api/photos/upload` call returns id + filename + caption; shows caption + "Indexed: filename"; storage usage bar fetched from `/api/storage` on load and after each upload; routed at `/caption`
- `src/pages/Search.tsx` — mode toggle ("Search by similarity" / "Search by keyword") above the search bar; text query → photo grid, similarity mode shows score %, keyword mode shows no score badge; hover-to-delete (`Del` label) with confirmation; click a thumbnail to open it in `PhotoLightbox`
- `src/pages/Gallery.tsx` — paginates all indexed photos via `/api/photos` (Load more button), same hover-to-delete pattern as Search, same lightbox-on-click
- `src/components/PhotoLightbox.tsx` — shared modal: larger image, caption (if present) with a pencil-icon edit affordance (textarea + Save/Cancel, `PATCH /api/photos/{id}` on save), score badge (if present — Search passes it, Gallery doesn't), a close button (top-right, `✕`) separate from the delete button (bottom-right, `Del`/`Confirm?`/`...`, drives the parent page's existing confirm-step delete state, no delete logic of its own). An optional `onCaptionUpdated` callback lets the parent page (`Gallery`/`Search`) update its own list state so an edited caption persists across lightbox close/reopen. Closes on backdrop click, Escape, or the `✕` button.
- `src/apiKey.ts` — localStorage-backed API key get/set, `installApiKeyInterceptors()` (called once from `main.tsx`) attaches the key to outgoing requests and surfaces a global prompt on any 401
- `src/components/ApiKeyPrompt.tsx` — modal shown when `apiKey.ts`'s interceptor sees a 401; saves the key and dismisses. Closable via `✕` button, backdrop click, or Escape (rendered after `<main>` in `App.tsx` so it stacks above an open `PhotoLightbox` rather than behind it).
- `src/index.css` — shared styles

### Testing (frontend)

```bash
cd frontend
npm install
npm test
```

## Triton model (`triton/model_repository/coca/`)

Single Python backend model. `config.pbtxt` defines two inputs (`input_data` bytes, `input_mode` string) and two outputs (`embedding` FP32[768], `caption` string). Unused output is zeroed/empty per request.

Model downloads from HuggingFace on first run (~1.5 GB, cached in `hf_cache` Docker volume). First startup after a fresh build will be slow.
